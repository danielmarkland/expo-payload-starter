# Neon migration execution record

The beta starter uses its own native Better Auth customer/editorial realms, PostgreSQL actor policies and independently administered Payload content. Portable product migrations and Payload migrations remain separate. Supabase SDKs, legacy authentication paths, generated Data API types, local services and release CLI dependencies are removed. Hosted setup now uses explicit environment configuration and preserves existing settings by default.

Two free PostgreSQL 17 projects in Daniel Markland’s Neon organization were created: `expo-payload-starter-dev` (`long-truth-63642346`) and `expo-payload-starter-prod` (`winter-thunder-55165611`), AWS us-east-1, fixed 0.25 CU, default scale-to-zero. Each has an isolated `neon-migration` rehearsal branch and three private buckets on rehearsal/main: `cms-media`, `app-uploads`, `site-transfer-archives`. No paid primitives, managed auth, Data API or Functions were provisioned. Parent/Postgres/object-storage skills and the HTTP Neon MCP configuration were installed without changing the existing Git Delivery skill; execution uses the authenticated CLI.

Promotion is feature MR -> develop -> main in this repository, with protected CI, development acceptance, then production activation. Schema changes promote; development records, users, files and secrets never overwrite production data.

The full `pnpm check` passes, including formatting, lint, type checking, integration tests and builds. All five browser tests pass on a dedicated local test database and port, including native editorial login, CMS navigation, contrast validation and public rendering. Authenticated requests to the exact feature preview return actual configuration/provider JSON and the search page from the fresh Neon backend. Product/Payload migrations and signed-write/read/anonymous-denial storage probes pass on all four main/rehearsal branches. Both main branches have a restricted `starter_runtime` login with identity, actor-profile and CMS role membership, without superuser, role/database creation, replication or RLS bypass; unscoped identity reads return no records. Matching runtime/migration and S3 credentials are installed in the GitHub development and production environments. A new development environment permits only the develop branch; existing production environment settings were preserved. Explicit configuration/provider/search smoke targets are configured in each release environment. The repository controlled-release switch is enabled after credential, runtime, storage and project-branch checks; feature promotion still requires current CI. Production-project tracked previews are delegated to that workflow.

Source local data is backed up in a protected temporary directory and remains intact. The user explicitly chose fresh starter databases and storage after the source inventory; no hosted source records or files were imported. The replacement Vercel token passed a CLI project/settings probe and was installed in all four approved GroovePost/starter GitHub release environments. Both starter Vercel projects now use their matching restricted Neon runtime and private storage credentials; existing Payload secrets, mail and provider configuration were preserved. Native auth secrets and explicit trusted origins were added. Cloud build commands no longer migrate; controlled releases own that step. The fresh CMS needs an initial linked editorial account and a configured identity provider before owner access. No source project has been deleted. Provider callbacks and live SMS/email require separate configured acceptance; no outbound messages were sent.
